## A 已确认的结论

**本次 MCP 最终成功返回，主要问题是首包前处理过重，以及分页把可用内容排在后面。**

调查对象是会话“对比视频与 TechPanel 项目”。`video_open` 工具记录耗时 355.103 秒。宿主等待约六分钟后收到结果，没有发现这次 MCP 调用抛异常或协议断开的证据。

命令行第一次确实失败：沙箱拒绝写入组件的登录锁文件。获批重试后运行 252.634 秒成功。两个入口使用同一核心与配置，命令行也没有立即返回。

## B 耗时主要发生在下载以后

| 北京时间 | 可核对的观察 | 含义 |
|---|---|---|
| 21:49:42 | 宿主发起 MCP open | 工具处理期间没有可消费的首包 |
| 21:50:04 | 源文件与字幕写入完成 | 下载已经结束，后续等待不能都归因于网络 |
| 21:50:06–21:53:13 | 初始取帧及局部稳定性检查；temporal 目录有 28 份 OCR 结果 | 默认启用数字／公式时间稳定性探测，普通软件界面也会进入此路径 |
| 21:53:18–21:55:44 | screen-verification 目录有 60 份 OCR 结果 | 自动字幕校验还会在首包前逐段做画面对照 |
| 21:55:44 | 生成冻结交付快照 | 取得源文件与向宿主交付内容，是两个不同时间点 |

文件修改时间是阶段证据，不能代替逐函数性能采样；但它与默认调用路径一致。`Reader._open` 先调用 `read`；`read` 默认做帧稳定性检查，再由 `_speech_page` 校验待审字幕，完成后才进入交付。

`Reader.read` 的处理范围由会话文件锁保护。原请求尚在处理时再用 CLI 打开同一视频，会等待同一把锁。两次 task 文本不同还生成了两个 read ID，各有 11 张帧记录；帧缓存按参数区分，不能把命令行后来成功解释成另一套更有效的读取引擎。

## C 已返回，但第一眼看不到内容

原 MCP 结果 `pages_in_snapshot=32`，第一页有续读游标，但没有原生图片块。正文与完整图像仍在后续页。

默认帧结果携带 OCR 文字与坐标。超量后，`delivery.pages` 先按对象顺序拆出全部字段，图片页排在文字碎片之后。这会让第一页主要显示 OCR 框坐标，难以立刻拿到字幕或画面。无损分页本身保住了数据，但首包组织不适合快速阅读。

该宿主最终还把约 5,811 tokens 的首包放进 2,500 tokens 的工具输出额度，日志明确标了截断；之后没有调用 `video_continue`。这是宿主消费问题，不能据此认定组件没返回，也不能靠删除源材料解决。

命令行的权限错误为 `PermissionError / WinError 5`，路径是 `auth/bilibili/.lock`。它说明缺少组件状态目录写权限，不是账号过期或平台拒绝，也不是锁已损坏。

## D 验证范围与后续处理

同一缓存经当前 MCP 读取 0–10 秒、指定一帧，并关闭新的 temporal/verify 处理：成功返回 7 段字幕、1 个原生图片块、1 页材料。端到端耗时约 27.3 秒；此数包含宿主工具层，不能用来声称核心处理很快。

另用组件原始 stdio 协议启动新进程复核：初始化约 0.969 秒，工具处理 0.031 秒，同样返回 7 段字幕和 1 张图片。此测试只说明该缓存读取及协议可用；不能拿它代替首次读取的耗时。

本次只排查并登记，未修改运行行为。优先改进点是：让已取得的字幕与画面先可用；把较重核查作为可继续执行的阶段；首包优先交付正文和图像；向宿主明确材料仍在处理、正在等待锁或需要续页。

沙箱下 CLI 需要对组件的 auth、data 等实际状态目录获得适当写权限；不删除登录锁，不清空凭据，不全局解除访问限制。

本案是“首包慢＋分页消费不完整＋CLI 权限受限”的组合。此前另一个案例的 `danmaku_unavailable` 根因仍未确认，不能凭本次结果一并宣称修复。


## E 运行状态与跨入口协作：对用户判断的源码核实

**用户判断基本成立：普通本地 open/read 缺少可靠的运行进度，也缺少跨入口的任务接续。**

需要区分三种状态：宿主知道调用尚未结束；组件知道材料是否 ready；组件向宿主说明当前运行阶段。前两种已有局部信息，第三种尚未形成可查询的契约。

| 判断 | 源码证据 | 本案影响 |
|---|---|---|
| 完成后才返回 | mcp_server.py:63–68 直接 pack(reader.open(...))；cli.py:192、240 在 Reader 返回后才打印 JSON | session_id、材料可用性和后续操作没有提前交给宿主 |
| 少量日志不是任务状态 | reader.py:668 向 stderr 打印提示；vision.py:231–234 每超过 25 秒打印核验进度 | 没有结构化阶段、心跳、锁拥有者或可用材料范围；MCP 没有调用进度通知 |
| 共享材料，未共享运行任务 | reader.py:246–289 复用会话与媒体；read/review 使用同一会话 FileLock | 两个入口能读同一份材料；新调用只能在锁上等待，不能查询或接续正在执行的工作 |
| 锁覆盖重处理 | reader.py:322–416 将抽帧、temporal OCR、字幕核验纳入会话锁 | CLI 改用同一视频时仍可能排队；日志未记录精确等待秒数 |
| 重试未复用同一个 read | reader.py:350–357 把 task 文本纳入 read_id | 本案两个 task 不同，形成两份各 11 帧的 read 记录；媒体复用不等于帧处理全部复用 |
| 已有 status 不等于运行状态 | review 的 status 也是先取得会话锁，再读校对覆盖；登录 status 验证账号 | 不能用这些接口判断 open 正在下载、OCR、等锁还是卡住 |

普通 open/read 的 MCP 入口没有 Context 进度上报参数，也没有组件级任务查询或接续工具。可选云端和复听另有局部任务机制，不能扩大为普通读取也有同等能力。FastMCP 的后台执行方式不改变这个业务接口缺口。

“没有任何反馈”仍不精确。组件有 stderr 提示，宿主也有工具运行中、命令会话运行中等外层状态。但这些信息没有告诉宿主：哪条业务任务正在执行、上次进度何时更新、哪些材料已可读，以及重复调用应该等待还是复用。

## F 因果关系与处理优先级

**状态缺失解释误判与重复调用，前置重处理解释首包慢，分页及宿主消费解释返回后仍不易读到内容。** 这三者需要分别处理。

1. 先让运行过程可识别。返回稳定任务 ID 和会话绑定，暴露阶段、最后进展时间、可用材料、等待对象与终态。状态查询不能再排到同一把长任务锁后面。
2. CLI 和 MCP 从同一份组件任务状态读取。重复的同源同参数处理应返回已有任务，允许继续等待或取得已完成材料。账号、分 P、区间与处理参数不同的请求不能只按 BV 强行合并。
3. 提前提供已就绪的字幕与画面。较重的核验保留明确状态与续作路径。只加进度条能改善判断，不能缩短那 355 秒的实际处理。
4. 首包优先给正文和图片，把较大的 OCR 坐标细节留作后续证据。宿主也应遵守续读游标，保留足够输出空间。

更改入口无需同步 Codex 的内部调用 ID；应由 Reader 自己提供跨进程稳定的业务任务 ID。进程还活着不等于正在前进，缺少心跳也不能直接宣判失败。

日志补充：21:53:59 宿主已直接读取缓存中 195 段字幕；21:54:23 经 view_image 看过 11 张帧。随后 CLI review 和 MCP 分页 review 继续提供字幕。最终得到内容由这些路径共同完成，不能全部归因于 CLI open。

本次以原会话日志、现存交付快照和上述源码核对；没有再下载视频或改动运行代码。未做新的逐函数采样，因此不分配精确 OCR/锁等待耗时。源码指纹及核对范围见 source-audit.json。
