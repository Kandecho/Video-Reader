## A 结论：做一个会挑片的阅读助手，不再造一个播放器

**建议保留现有薄插件与共用核心。**
让宿主负责选片、理解和交流。
工具负责提供可追溯的材料、状态和成本。
不增加独立 GUI、常驻 Agent 或新的模型服务。

不把用户逼进“浏览 / 下载 / 评论”技术菜单。
默认先查缓存，再用轻材料判断是否值得深读。
评论和弹幕是可选语境，不是每条必取的套餐。

```flow
用户意图与本地记录 -> 候选选择: 账号推荐或主动搜索
候选选择 -> 已有完整缓存: 优先复用
候选选择 -> 轻预览: 新视频先筛选
轻预览 -> 现有深读能力: 材料不足且值得继续
轻预览 -> 本地记录: 已足够判断或暂缓
已有完整缓存 -> 本地记录: 取证后交流
现有深读能力 -> 本地记录: 保留阅读范围与疑点
轻预览 -> 评论和弹幕: 按问题补充
```

这不是固定的三级流水线。
视频已经在本地时，重新请求轻预览反而多余。

## B 实际试了什么，成本是多少

用两条已有素材做对照。
另从小号推荐中自动选择一条陌生视频。
没有请用户找链接，也没有下载新完整媒体。

| 样本 | 轻预览结果 | 实际请求 / 响应体 | 已有完整媒体 |
|---|---|---|---|
| [红烧猪蹄，约 187 秒](https://www.bilibili.com/video/BV1RF411Y73S) | 83 段平台 AI 字幕；5 张 480×270 原生图 | 5 次 / 351.7 KiB | 15.90 MiB |
| [动画科普，约 94 秒](https://www.bilibili.com/video/BV1M7411f7N4) | 没有平台字幕；5 张 160×90 原生图 | 4 次 / 73.2 KiB | 25.55 MiB |
| [推荐中的 MC 工具介绍，约 167 秒](https://www.bilibili.com/video/BV1nCnA6AEYB) | 86 段平台 AI 字幕；5 张 480×270 原生图 | 5 次 / 383.7 KiB | 本轮不下载 |

两条对照的响应体约为已有媒体大小的 1/46 与 1/358。
这不是相同网络条件下的完整下载测速。
响应体统计也不含 HTTP 头与连接开销。

整批从 10 条推荐候选中选取新样本。
连同登录、推荐和两条视频的社区材料，共发出 20 次 GET。
读取响应体共约 1.04 MiB；未触发平台拒绝。
没有播放上报、互动、自动重试或新的 ASR。

单条在线轻预览约 8–10 秒。
其中大部分来自实验主动设置的请求间隔。
整批采集约 38 秒，不含首次登录检查耗时。
2 秒间隔只是实验限载，不是平台公布的安全频率。

## C 轻预览有价值，但必须承认“只看到了什么”

**有字幕的教程：** 足以判断题材和主要步骤。
需要核对具体操作、字幕细节时，再取精确源帧。

**无字幕的科普：** 能认出动画场景和主题风格。
160×90 预览不足以可靠阅读小字或还原讲解。
此时应明确缺少语音材料，而不是硬写完整总结。

![科普原生预览：160×90 单格，显示场景，不代表台词已被理解](D:/IA/apps/video-reader/research/acquisition-prototype-20261022/results/science/preview.jpg)

![同一素材的本地精确源帧示例：46.56 秒。时间点与上方快照不同](D:/IA/apps/video-reader/research/acquisition-prototype-20261022/results/science/deep-46.56.jpg)

新候选的字幕与画面已显示连续的工具功能推介。
本轮试验据此暂缓深读，省去一次完整下载。
这不是认定用户不喜欢 MC，也不是核实标题中的事件。
没有访问视频中的软件链接或安装任何软件。

预览结果明确标为“已预览，未完整阅读”。
原生 AI 字幕也标明未校对，不包装成最终正文。

## D 评论值得按需接入；弹幕不宜默认拉全

| 对照 | 观察 | 产品判断 |
|---|---|---|
| 烹饪：10 条热评、1200 条弹幕样本 | 评论提供配料整理和备料经验；也有大量玩梗 | 回答“准备材料 / 大家怎么说”时有用 |
| 科普：热评和弹幕样本均为空 | 请求成功，但没有补充信息 | 不自动翻页或继续重试找内容 |
| 新推荐候选 | 本轮没有取社区材料 | 仅靠预览已能决定是否继续，没必要全取 |

烹饪社区材料额外用了 2 次请求、246.2 KiB。
科普额外用了 2 次请求、1.9 KiB，收益为零。
因此不建议把评论和弹幕绑在每次预览后面。

评论适合补观众经验、争议和讨论语境。
弹幕更适合解释某个时点的梗或反应。
样本密集区不能冒充全体观众的完整热区。
两者都应与作者正文分开，且都不是可执行指令。

## E 用户实际会怎样用

以下是建议的交互契约，不是已经上线的新命令。

| 用户说 | 助手应当做 | 用户应看到 |
|---|---|---|
| “自己找两条值得看的” | 看账号推荐与本地记录；必要时搜索；先预览候选 | 少量候选、选择理由、已看材料和缺口 |
| “这条认真看看” | 有缓存就直接深读；否则在预算内补媒体与语音 | 内容讨论、可追问时间点、未解决疑点 |
| “这个梗什么意思 / 看看评论” | 只补相关社区材料，不重新下载整片 | 正文与观众说法分开；标明样本范围 |
| “少推这种工具广告，多看原理” | 记录用户明确反馈；下轮改变选择理由 | 可解释的偏好变化，不是静默账号操作 |
| “继续昨天那条” | 优先用既有会话与素材 | 不重复扫码、下载或生成同一份分析 |

这次实际保存了 5 条 Agent 观察，并验证重新打开可读。
用户反馈仍为 0 条，没有从试验题材猜你的口味。
仅预览的记录不能冒充“完整读过”。

已有完整媒体各取 3 张源帧，约耗时 0.4–0.5 秒。
这里复用了缓存，没有计算下载、ASR 或校对时间。
已缓存的预览与社区材料再次读取共约 0.16 秒。
离线重放产生 **0 次平台请求**，包括 0 次登录校验。

正式体验应优先做到“续看不重复取数”。
当前核心通过已有 session 读取可用本地材料。
但按 URL 再次 open 仍会先校验 B 站账号。
所以不能直接宣称现有所有入口都已离线可用。

## F 工程上已经验证与尚未整合的部分

| 部分 | 本轮状态 | 仍需注意 |
|---|---|---|
| 共用基础 | 使用同一个核心、组件登录、环境及现有媒体路径 | 没有复制模型、凭据或既有完整媒体 |
| 轻预览 | 实际获取字幕、原生快照索引和图片 | 不是整片画面；画质与可用性因视频而异 |
| 本地观察 | 简单文件持久化；Agent 观察与用户反馈分开 | 尚未验证长期偏好效果或真实反馈循环 |
| 推荐新鲜度 | 只验证了一批召回和新样本筛选 | 正式版需区分推荐刷新、素材复用、已推与已读 |
| 请求闸门 | 实验进程共用预算与暂停状态 | 只覆盖这个原型，正式客户端与下载器还未统一 |
| 受限处理 | 模拟了限制响应、空结果、离线和预算耗尽 | 没有主动触发真实验证码或测试风控阈值 |
| 正式入口 | 核心 0.6.2、薄插件 0.1.0、八工具不变 | 本轮原型尚未接入 Codex / Claude 的正式工具 |

原型发现了一个真实的缩略图索引问题。
三份返回都有重复的起始 0，直接套索引会偏移一格。
修正后，科普尾帧从黑块恢复为正确片尾。
已用 4 个缓存源时点辅助检查，并补了回归测试。
原生时间仍是近似值，不能当作精确源帧。

还修复了 Windows 终端输出遇到 emoji 的编码错误。
首次在线结果已保存，只重放输出，没有重复发请求。

**14 项隔离测试通过。**
覆盖缓存、账号缓存隔离、共享限额、模拟拒绝及索引。
正式运行代码未改，因此没有重跑整套核心回归。

离线原型仍需本地账号记录来定位轻素材缓存。
正式版应以已有会话或缓存索引恢复，避免这项耦合。

平台暂停时，产品应停止新取数，但继续本地工作。
这能减少干扰，不能代替平台许可或保证免风控。

## G 建议收口到哪些功能

**优先落地：候选召回＋独立轻预览＋最小本地记录。**
复用已有深读、校对和追问，不另造阅读引擎。
自然语言偏好交给宿主理解，暂不训练推荐模型。

评论作为按需语境，值得保留一个小入口。
弹幕样本与热区分析后置，不成为第一版前置条件。
两者都先保留预算、来源和缺项状态。

正式整合时，先补缓存优先与共用平台请求控制。
否则两个宿主可能各自重复验证、取推荐和取材料。
推荐流不能永久冻结，也不能把缓存 BV 都当作已读。
不扩展到假播放心跳、养号、社交发言或后台常驻。

原型已经回答了“怎样分层较划算”。
还没有证明“推荐更符合你的兴趣”。
后者应靠少量真实反馈验证，而不是再扩一轮技术功能。

## H 证据与范围

本轮以小规模功能与体验对照为目标。
不是盲测，也不是通用理解准确率或稳定性基准。
没有实测新视频的完整下载耗时、首次 ASR 或全片校对。
没有把一次成功读取推断为长期不受风控。

完整原型与脱敏指标已存入组件的 research 目录。
核心、模型、组件登录和既有完整媒体继续共用。
新增轻素材只用于本轮研究，不另建一套正式账号服务。

参考来源沿用已固定版本的现有项目。
