# Video Reader 独立工具方向调研与讨论

2026-10-24

身份：当日跨领域广搜的讨论报告，整理时归入项目。未重新联网、安装或复测外部项目。本文建议不是已批准接口；其中“现有说明偏全量”不应读成不支持局部读取，当前 Skill 已明确允许局部区间问题。后续图文试验和输出缺陷见[真实输出案例](../output-reuse-20261024/report-source.md)，当前状态以[路线](../../planning/roadmap-20261021-source.md)为准。

**我建议继续做可独立接入的 Video Reader，但把对外承诺落在“视频材料能被不同 Agent 稳定使用、按需展开、回到原片核查”上。** 当前已经有读取核心、分页、原文与校对关联、MCP 图片和薄插件，不需要重建。最值得补的部分是稳定的数据契约、首次长任务体验，以及真实的跨宿主交付。

广搜也修正了一点判断：已有多个公开方案组合本地抽帧、转写、时间戳、MCP 和渐进读取，不能再把这些功能本身当作独特优势。比较时应看同一个任务中，哪些材料实际到达了模型、引用是否能复查、失败能否继续，以及用户要花多少安装和维护时间。

本报告以现有 0.8.0 安装及本地修复为项目基线。外部项目采用本轮查阅的官方文档、仓库说明和少量源码入口比较；没有安装它们，也没有做同环境效果排名。沿用此前已经确定的本地默认、云端不自动回退、Reader 与 Scroll 分工，本轮只报告讨论结果。

**一、名称之外，哪些项目实质上在解决同类问题**

检索分为视频理解、媒体检索、文档转换、网页读取、语音处理、代码导航、浏览器工具、上下文管理及来源定位等方向。关键词包括 `video understanding / video context / evidence ledger / bounded retrieval / document provenance / structured extraction / lazy loading / tool output / media fragments / multimodal search`，并回查已有 BiliLearn、bili-cli、DSH scroll、humanism 及转写校对调研。

此前对 BiliNote、VideoLingo、pyVideoTrans、WhisperX 等八个项目的比较，已经明确了笔记生成、忠实校对和时间对齐的区别。现有“宿主判断和校对，组件保存原文与依据”的职责值得保留。这轮补充的是材料怎样跨宿主交付和复用，不需要为公开重新部署一个专门的总结或校对模型。

下表前三项是较直接的同类工具；文档、代码、浏览器项目是接口设计参照；WhisperX 属于处理能力，云视频服务则代表另一条实现路线。它们不是同一种竞品，但都涉及把原始来源整理成可定位、可分段取用的材料。

| 方向与代表 | 与我们相同的实质 | 值得借鉴的部分及区别 |
|---|---|---|
| [VideoContext MCP](https://github.com/sakshamjain2301/videocontext-mcp) | 本地把视频转成时间线、字幕和可选择的画面，按范围及续读令牌交付 | 是很近的参照。准备与读取分开，图片先预览再取原尺寸，产物有资源 URI 和删除入口。其说明仍要求较长工具超时，不能把 job ID 等同于异步任务已经完善 |
| [mcp-video-analyzer](https://github.com/guimatheus92/mcp-video-analyzer) | 链接或文件进入，文字、画面、OCR 和时间线出来 | 同时提供 CLI JSON、MCP、局部片段和批量处理。说明明确区分“少返回字段”和“实际少做处理”：过滤输出未必省去下载或抽帧 |
| [timecode-agent](https://github.com/mupozg823/timecode-agent) | 先定位材料，按需视觉核验，留下时间与来源绑定 | 从剪辑领域切入，仍是“材料—证据—下游消费”。可借鉴修订绑定和可重建输出；其剪辑、知识页、技能生成等业务不适合一起纳入 Reader |
| [Docling](https://docling-project.github.io/docling/concepts/docling_document/) 与 [Docling MCP](https://github.com/docling-project/docling-mcp) | 将不同原件归一成保留结构和出处的数据，再交给不同消费者 | 很有价值的类比：原件位置和内容项身份属于数据模型，Markdown 是一种呈现。对视频而言，时间范围相当于文档页码与区域。无需采用其整套文档模型 |
| [Kreuzberg](https://docs.kreuzberg.dev/guides/mcp-integration/) | 同一提取引擎供程序、CLI 和 MCP 使用 | 借鉴核心与接入层共用配置和数据。它的多格式、嵌入与结构化生成能力说明可扩展空间，也说明没有必要全照搬 |
| [MarkItDown MCP](https://github.com/microsoft/markitdown/blob/main/packages/markitdown-mcp/README.md) | 用很薄的工具入口把来源变成 Agent 可读内容 | 单一转换入口容易理解；我们还需要时间定位、图片、来源版本和继续读取，不能只以一份 Markdown 作为唯一输出 |
| [Firecrawl](https://docs.firecrawl.dev/features/batch-scrape) | 输入 URL，准备可消费材料，区分同步返回与长任务 | 异步入口返回任务 ID，另查状态、错误和结果。可借鉴任务交付方式；网站爬取、搜索与研究 Agent 不应跟着进入 Reader |
| [WhisperX](https://github.com/m-bain/whisperX) | 把连续媒体整理为带时间的可计算片段 | 识别、对齐、说话人分离是可拆分的处理能力。识别文字与时间估计各有误差，校对文字不能悄悄继承“逐字精确”含义 |
| [Serena](https://github.com/oraios/serena/blob/main/src/serena/tools/symbol_tools.py) | 先给可定位的结构，再按需取正文 | 代码符号概览、定位与函数正文，对应视频目录、时间段与片段材料。说明按需披露的关键是可靠地址和继续读取能力，不只是一份较短摘要 |
| [Playwright MCP 的快照](https://github.com/microsoft/playwright.dev/blob/main/mcp/snapshots.mdx) | 用结构化观察与引用连接后续动作，必要时补图片 | 它明确引用的适用范围和失效条件。我们同样需要说清：某个段落 ID 属于哪个字幕版本，旧校对是否还能用于新材料 |
| [context-mode](https://github.com/mksglu/context-mode) | 大结果留在上下文外，需要时检索原文片段 | 可以参考小结果与按需读取的接口；不应为此接管整个宿主的路由、会话记忆或钩子系统，也不直接采用其宣传的压缩比例作为我们的收益 |
| [TwelveLabs](https://docs.twelvelabs.io/v1.3/docs/get-started/quickstart/search) 与 [VideoDB](https://videodb.io/blog/why-a-search-tool-is-not-enough-for-an-llm-working-with-video) | 视频建索引，问题返回带时间范围的材料或答案 | 更适合反复查询大视频库。值得学“搜索命中不等于完整计数”的区别；当前逐条读取不必先建设视频数据库 |
| [Gemini 视频理解](https://ai.google.dev/gemini-api/docs/video-understanding) | 直接接收视频，也能按问题访问文字、画面和声音 | 是必须纳入比较的替代方案。模型服务本身已有按需导航，不能将渐进读取视为我们独有；本项目的本地处理、材料留存与跨宿主使用仍有独立用途 |

还有一个跨领域参照是 [W3C 的 Selectors and States](https://w3c.github.io/web-annotation/selector-note/)：引用可以表示“哪个资源、其中哪一段、哪个状态”。这支持把原片定位与材料版本分开保存；第一版无需引入整套 JSON-LD 或标注服务。

最值得后续细比的是 **VideoContext MCP 的材料接口、timecode-agent 的证据修订、Docling 的数据与呈现分离**。现有 DSH 案例继续用于检查宿主接驳、权限边界和发布渠道，不再承担定义整个 Reader 产品的角色。

**二、谁需要它，实际想完成什么**

首批对象可以收窄为已经在使用多模态 Agent 的个人用户和集成开发者。前者希望把视频直接带入现有讨论；后者希望接入一个可预测的读取组件。无需要求他们迁入新的笔记应用或长期视频管理系统。

| 使用要求 | Reader 应交付什么 | 判断是否有价值 |
|---|---|---|
| “这条讲了什么，哪些地方值得继续看” | 低成本概览、可用字幕与画面状态、继续深入入口 | 第一次有用结果能否较快出现，是否知道它只是预览 |
| “认真读完，保留细节” | 全范围文字分页、全片画面抽样及必要补看，明确缺口与校对状态 | 分页有没有漏，材料是否足以支持所做总结，而非只看开头 |
| “核对 06:12 的插件名或图中数字” | 指定时点原图、附近原文与改动依据，需要时短段复听 | 能否直接查证，不必重做整片 |
| “今天换个 Agent，继续昨天那条” | 可恢复的材料身份、版本、已完成处理和可用附件 | 是否重复下载、转写；是否需要重新猜本地目录 |
| “把这段用于项目讨论或知识库笔记” | 可引用片段及来源，不绑定笔记模板 | 下游能否保留出处，自行决定组织方式 |
| “整套系列哪些集有增量” | 各视频可复用材料，清楚的逐条状态 | 系列编排及与个人知识比较由宿主做，失败一条不抹掉其他结果 |

这里有个重要区别：**按需披露是交付策略，不是把用户所有需求都变成“只看几帧”。** 用户要完整阅读时仍要提供相应范围和分页；用户只问一句话时，不宜强迫完成全片校对才准回答。现有 MCP 操作说明偏向完整阅读和全量校对，应在以后适配时区分任务所需的范围，而不是降低完整阅读的要求。

**三、理想输入保持简单，复杂性由调用层承担**

人的默认输入仍是一条链接、BV 号或本地视频，加一句需求。程序输入可分三层，第一层必须明确，后两层可有合理默认值。

| 输入层 | 建议内容 | 原因 |
|---|---|---|
| 来源 | 视频链接／BV／本地文件；必要时分 P、外部字幕 | 先确认到底是哪份媒体。合集链接应先解析为条目清单，不能静默只读第一集 |
| 本次范围 | 整片、时间区间、精确时点；所需文字／画面／证据 | 允许“只取 3–5 分钟”和“完整读取”共用底层，避免为小问题先跑全片 |
| 执行约束 | 缓存优先、可用来源、语言、返回大小与图片数量等 | 把处理成本和返回体量分开；引擎高级参数保留给明确需要的调用方 |

问题文本可以帮助调用方选择片段，但读取组件不必据此自行写结论。用户项目背景、长期偏好、私信对象、知识库写法仍由宿主管理。

“链接”在首批支持范围中应指向可解析的视频或视频集合；普通文章和 PDF 已有成熟读取工具。保持共同的出处表达，有利于下游把它们放在一起使用，不必让 Video Reader 同时成为网页和文档解析器。

**四、输出需要兼顾程序、人和模型，但共享同一份材料**

建议把“可保存和交换的材料结构”与“本次给模型的阅读页”分开。材料结构保存身份、来源、时间及关联；阅读页只返回本次需要的内容。MCP、CLI、直接函数调用都由这份结构生成，避免各自维护一套语义。

| 输出内容 | 最少应回答的问题 |
|---|---|
| 来源身份 | 哪条视频、哪一分 P、哪份本地文件或字幕？材料取自何时、何种来源？ |
| 材料版本 | 这次字幕、ASR、校对是哪一版？段落与图片 ID 在什么范围内稳定？ |
| 时间定位 | 原片的起止秒数是什么？近似预览还是精确取帧？可点击的原片入口是什么？ |
| 材料正文 | 文字来自平台字幕、ASR、OCR 还是宿主校对？图像如何实际取回？ |
| 范围与状态 | 已处理哪些范围、本页返回哪些、还有哪些页、哪里失败或仍不确定？ |
| 继续使用 | 怎样取下一页、展开原文和改动依据、取得原图、恢复任务？ |

这些是待讨论的数据语义，不是现在就冻结字段名。尤其应区分三种身份：**视频本身、一次处理任务、某份材料的修订版本**。任务结束或会话切换，不应让原片引用失效；换引擎或改字幕，也不能让旧段落 ID 悄悄指向不同文字。

以一个局部问题为例，理想返回应让宿主直接知道：

> 来自某 BV 的第 1 P，原片 06:12–06:25；本页含相关字幕段和一张源帧。字幕有一处已校对，依据可以展开。画面只覆盖这些时点，未做连续动作判断。可以继续取后续片段，也可以打开原片核对。

程序从相同数据取得 ID、秒数、版本和附件引用；人看到易读文字与链接。不要让程序从这段中文里反向解析状态。

建议保留两个回查入口：**原平台的定位链接**用于人回看；**组件的材料引用**用于 Agent 精确取回原文、图像和校对依据。平台视频可能删除，本地缓存也可能清理，因此还需区分“来源仍可定位”和“证据文件目前仍在”。初期可以由已保存的轻量清单加按需读取完成，无需自建长期档案馆。

完整 JSON 适合交换，带时间的 Markdown／VTT 适合阅读或导出，原生图片块适合模型查看。正文先给多少，应受调用范围和大小上限控制；只给一个资源链接而没有可用的取回方式，不算完成交付。

**五、跨 harness 的重点是验证材料到达模型，不只是连接成功**

harness 指 Agent 的运行宿主，例如 Codex、Claude Code、Gemini CLI 或 DSH。它负责工具调用、结果转给模型、文件访问和会话生命周期。MCP 连接读取工具与宿主；模型 API 的图片、音频、视频输入则是另一层。支持 MCP 不自动等于所有媒体都能被模型看到。

关系可以明确为：**核心产生统一结果；CLI 和 MCP 是调用入口；宿主薄插件负责把 MCP 接入宿主并提供使用说明，必要时转换附件。** 这里的统一结果指拟整理的公开契约，现有内部字典与缓存结构提供基础，并不等于已经完成这一契约。

各部分的职责是：

- 核心函数／CLI JSON：供脚本及非 MCP 调用方使用；同机文件通过受控路径读取。
- MCP：标准工具调用、当前页文字与图片，需要时提供资源读取；作为主要 Agent 接口。
- 宿主薄插件：安装配置、少量使用说明及必要的附件适配。只在实际差异出现时增加专用代码。

| 宿主或接口 | 已有依据 | 对我们意味着什么 |
|---|---|---|
| Codex | 本机已有工具调用及原生图片验收；官方配置有工具超时设置 | 继续作为已验证路径，但冷启动、长任务及新版本仍要分别判断；官方默认超时不代表本机实际配置。[官方说明](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) |
| Claude Code | 已有薄插件格式校验，尚无本项目实际安装验收；官方说明支持 MCP 图片，且可能缩放图片、将大结果保存到文件 | 同一页文字和图片是否到达模型，需要真实调用检查；安装清单通过不能替代。[官方说明](https://code.claude.com/docs/en/mcp) |
| Gemini CLI | 官方文档说明会将 MCP 多内容块转换给模型，包含图像、音频及资源类内容 | 可作为后续验证对象；不据文档声称本项目已兼容，也不等于要启用本项目 Gemini 云端读取。[官方说明](https://geminicli.com/docs/tools/mcp-server/) |
| DSH 等原生插件宿主 | 既有 humanism 静态调研显示其有原生工具注册及媒体交付约定 | 能用 MCP 就先用；确需原生附件适配时，从共同结果结构转换，避免复制取数和转写链 |
| 远程 Agent／容器 | 读取进程和模型宿主不一定共用文件系统 | `D:/.../frame.jpg` 不能成为唯一契约。需要真实图片内容或可访问的资源读取方式；HTTP 服务是部署选择，不是首版必需 |

MCP 目前可以表达文字、图像、音频、资源引用及结构化结果，并可用 `outputSchema` 说明结构。**这解决了包装格式，视频段落、来源版本、覆盖范围仍需要我们定义。** 图片型入口现有代码使用“JSON 文本＋原生图片块”，不是毫无结构；需要评估的是是否统一成版本化的公开结果契约，以及如何同时服务机器读取和旧客户端。[MCP 工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

MCP Tasks 已有长任务扩展，但需客户端协商支持。建议核心先具备清楚的任务状态、进度、取结果和取消语义，MCP 支持时映射过去；不支持的宿主仍能通过普通工具取得相同状态。进度通知不保证延长宿主硬超时；客户端关闭也不自动意味着所有子进程都已停止。[Tasks 扩展](https://modelcontextprotocol.io/extensions/tasks/overview)

[Agent Client Protocol](https://agentclientprotocol.com/get-started/introduction) 主要连接编辑器与编码 Agent；它不要求一个读取工具也实现 ACP。对我们的直接消费边界，MCP 和普通程序接口已经是优先选项。

“本地处理”还需准确表述：媒体获取、抽帧和转写可以在本地，**交给远程宿主模型的文字和图像仍会离开本机**。这应在接入说明里讲清，不能用“本地优先”承诺全程离线。

**六、对照项目现状，工程工作应落在哪些具体缺口上**

| 事项 | 当前基础 | 需要补足或进一步确认 |
|---|---|---|
| 独立读取与接入 | Reader 类、CLI、9 个通用 MCP 工具，Reader／Scroll 已拆分 | 对外最小包能否独立安装；不为公开再造一层业务平台 |
| 通用结果 | 已有结构化字典、缓存 manifest 的 `schema_version`、来源、时间、片段、分页与证据状态 | 缓存版本不等于公开接口版本；需明确哪些字段对调用方稳定、哪些为内部细节 |
| 按需读取 | 已有预览、文字／图片分页、区间、精确时点、reading/raw/evidence | 工具说明和返回量应区分预览、局部核对、完整读取；精简输出还要对应实际少做处理 |
| 长任务 | ASR 已有分段恢复，复听有独立 worker 和期限 | `open` 仍同步进入 read，首次 OCR 会拉长调用；没有统一、可跨连接取得的准备任务接口 |
| 证据与版本 | 原文留存、校对快照和修订校验、来源隔离已有实现 | 从会话及本机路径进一步整理成清楚的材料身份；错误版本、失效缓存和来源变化应有可处理结果 |
| 多宿主 | Codex 本机实用；Claude 薄包格式校验；共享磁盘资源 | 补实际声明支持的宿主，检查原图、分页、截断、重连、取消；不能用“支持 MCP”代替支持矩阵 |
| 运行成本 | 缓存复用和局部读取有效；不同宿主仍各自启动 stdio 进程 | 防止同一材料重复重处理及 GPU 同时加载；先考虑文件锁和有界执行，不预设常驻 GPU 服务 |
| 发布与维护 | 现有依赖清单、许可调查、bootstrap、公开候选路线 | 干净安装、真实分发入口、可诊断错误、更新兼容；运行目录不能整体公开 |

长任务值得优先处理的依据很具体：此前 Windows 管道继承和 NumPy 加载卡顿已修复；诊断阶段经提前加载依赖后，首次默认 OCR 的 `open` 约 370 秒。最终正式入口的 0.14 秒复读复用了这些缓存，尚未重新测得正式入口的冷缓存耗时。仅把超时配置调大不能解决等待期间无明确状态、重连后不知做到了哪里的体验。

成本至少要分开看：第一次有用结果的等待、完成所需范围的时间、返读时间、下载与本地资源消耗、宿主输入量及校对调用量。省下文字长度不等于省下 OCR，少返回几张图也不等于任务更便宜。不能观察到的宿主费用应保持未知。

错误结果应区分未登录、来源不支持、取数失败、材料没有取得、处理超时、部分完成和引用过期。让调用方知道下一步是登录、缩小范围、继续任务还是换来源。没有字幕不能直接说没有语音，取不到图片不能继续声称已经核对了画面。

现有路线已经覆盖组合任务验证、边界守护、清洁源码基线、许可与干净安装。这轮新增的重点是把它们具体化为：**结果契约、长任务生命周期、材料引用、宿主能力实测和按问题选择读取范围**。它们应补入原主维护处，不再另建一套重复路线。

**七、建议用少量完整任务决定继续投入什么**

之后若进入验证阶段，可以沿用原路线的 2–3 个短任务：一条字幕与画面有冲突的教程、一条无字幕且中断后继续的视频，再加一次材料交给另一宿主追问。输入、问题和模型条件尽量一致，对照“直接字幕／简单抽帧”及一个最近的同类工具；只有允许云处理时，才增加原生视频 API 对照。

评估应落在：回答中的关键事实是否有材料支持、能否回查、是否漏页、重试是否重做已有工作、首次与返读成本、用户需要多少手动修补。某类任务简单字幕就足够，应如实保留这个结论。完整阅读不能用命中几段来替代，定点问答也不必强制全量处理。

首批公开范围建议优先选择已实测的 **Windows、本地视频和 B 站、Codex**，完成 Claude 的真实验收后再声明它。代码可保留扩展入口，但不把 YouTube、多语言、所有 harness、完整声音语义都设为首次公开的前置条件。

公开有用并不要求技术独有。如果别人更成熟，我们可以复用其非关键实现；值得自己维护的应是已经证实的使用需求、数据约定和平台经验。现在最有希望形成吸引力的是：**在现有 Agent 中直接讨论视频，得到可复用、可核查的材料，并且安装和持续使用不麻烦。** 这一组合是否明显优于现成方案，还需要上述任务对照来证明。

**八、接下来值得讨论的三个取舍**

1. **默认第一次返回多轻？** 我倾向先返回身份、可用材料和一小页，重处理有独立状态；对明确“完整读取”的请求由宿主继续推进，而不是让用户手动管分页。这影响首屏等待，也影响旧接口兼容。
2. **哪些材料需要跨会话保留？** 我倾向保留轻量来源清单、文字和修订关系，把媒体缓存设为可管理；跨机器导出完整证据包可后置。否则“可回查”容易依赖一直不能清理的缓存目录。
3. **首批兼容承诺有多大？** 我倾向少量宿主真实验证，而不是列很多可配置名称。可维护的共同核心和转换层比一开始适配十几种宿主更重要。

这些取舍会实质影响工程量。JSON 字段命名、工具拆成几个、是否提供额外导出格式，可以在选定使用方式后由实现解决，不需要现在逐项让用户决定。
