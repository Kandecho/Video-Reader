## A 先明确“避免干扰”的含义

目标是减少不必要访问，并让受限后的恢复可控。
不以伪装真人或保证机器人不被识别为目标。

**低频、只读、独立小号，都不自动等于平台许可。**
当前用户协议 5.6(3) 限制未经书面许可的自动取数。
工程护栏不能代替平台授权。
[B 站用户使用协议](https://www.bilibili.com/blackboard/protocal/licence.html)

本轮参考项目没有提供可验证的免风控保证。
能借鉴的是能力拆分、缓存、限额和停止机制。
不是照搬“随机等待后就安全”的假设。

## C 建议研究的是“主线＋旁路”，不是三级套餐

```flow
账号推荐与关键词搜索 -> 元数据初筛: 不取完整媒体
元数据初筛 -> 轻预览: 需要更多依据时
轻预览 -> 下载后深读: 轻材料不足时
元数据初筛 -> 评论与弹幕: 按问题选取
下载后深读 -> 评论与弹幕: 需要观众语境时
```

| 候选能力 | 获取什么 | 不代表什么 |
|---|---|---|
| 浏览 | 推荐、搜索、标题、简介、时长等元数据 | 不代表看过内容 |
| 轻预览 | 可用字幕、封面或原生时间轴缩略图 | 不代表完整画面理解，也不保证总能拿到字幕 |
| 下载后深读 | 复用现有下载、抽帧、转写和校对 | 不代表平台已记录正常播放 |
| 社区语境旁路 | 有界热评、相关弹幕片段或采样 | 不是作者原话，不是全体观众意见 |

评论和弹幕可以在下载前读，也可以完全不读。
“不下载”应指不取完整媒体，不是零网络字节。
字幕、封面和缩略图本身也需要传输。

这些是待验证的能力边界，**不是本轮确定的接口设计**。

## D 对当前 Video Reader 的影响

**已有轻入口：** search / discover 只返回候选元数据。
**现有缺口：** 首次 open 会进入媒体获取流程。
它不是字幕或原生缩略图优先的独立轻预览。

推荐与阅读仍共用一个核心、登录和缓存。
分层是取数策略分开，不是再复制一个应用。
评论和弹幕若接入，应保留来源、时间及采样口径。
弹幕样本的密集区不能直接冒充全量热区。

本地至少要区分“发现、预览、实际阅读、评价”。
缓存只是素材状态，不等于已经阅读。
Agent 自己的评价与用户反馈也应分别记录。
本地评价不自动变成账号点赞、收藏或播放上报。

## E 怎样减少对正常使用的干扰

| 控制点 | 候选做法 | 为什么有用 |
|---|---|---|
| 取数前 | 先查共享缓存；先筛候选，再深读少量视频 | 减少本来不必发出的请求 |
| 账号身份 | 按功能明确是否需要组件登录 | 不将“匿名访问”当成受限后的逃生通道 |
| 多宿主 | Codex 与 Claude 共用账号级请求预算和冷却状态 | 多个进程的请求不能各自从零计数 |
| 平台拒绝 | 区分网络瞬断、登录失效与限制响应 | 不把风控误报成“没有视频或评论” |
| 恢复方式 | 瞬断仅有界重试；验证挑战或限制时停止新增平台取数 | 不让 Agent 自动重试形成请求风暴 |
| 受限期间 | 已下载视频仍可本地阅读、转写和评价 | 平台暂停不必阻断本地工作 |
| 账号写入 | 与读取完全分离，默认不开 | 不因借用推荐模块顺带上报历史或互动 |

当前核心**还没有**统一的账号级平台预算与冷却。
认证锁、视频缓存锁也不等于统一请求限流。
未来还需覆盖下载器子进程，不能只管一个 API 封装。

不从参考项目复制所谓“安全每分钟请求数”。
没有经验证的统一安全频率。
本轮也没有测试平台的限制阈值。

不采用代理轮换、指纹伪装或验证码绕过方案。
也不补造观看进度来模拟真人行为。

## F 这次实际验证了什么

2026-10-22 00:32（北京时间），复用组件自己的凭据。
没有读取浏览器或其他项目的账号文件。

| 探测 | 结果 |
|---|---|
| 登录校验 | nav 返回 code=0；组件账号仍有效 |
| 账号推荐 | 一次推荐 GET 返回 code=0；含 5 条有效 BV 候选 |
| 主动平台请求 | 两次 GET；无重试、无凭据续期 |
| 媒体与账号写入 | 无媒体下载、无播放上报、无点赞收藏或发言 |
| 数据留存 | 只留脱敏状态与数量；未保存推荐标题、UID 或 Cookie |
| 正式版本 | 核心仍为 0.6.2；插件仍为 0.1.0；八个 MCP 工具不变 |

这只证明当前登录与单次推荐链路可用。
没有证明持续运行安全，或平台允许自动化。
也未实测评论、弹幕与原生缩略图的可用性。

“只读”表示没有主动调用账号写接口。
它不表示服务端没有访问或行为日志。
平台政策包含浏览、播放、点击、下载等日志类别。
[B 站隐私政策](https://www.bilibili.com/blackboard/privacy-pc.html)

我们目前没有主动发送播放器心跳或观看进度。
但没有验证服务端是否将获取行为计入历史或播放量。
因此不能承诺“平台绝对不知道账号读过这个视频”。

## G 下一轮 Spike 应回答的三个问题

1. 轻预览能否只取字幕和原生缩略图，不触发完整媒体下载？
2. 只看正文、补热评、补弹幕，分别能改善什么判断？
3. 平台取数暂停时，本地读片能否继续，并明确报告缺项？

建议用少量有字幕和无字幕素材对比。
记录实际请求数、传输字节、耗时和材料缺失。
比较每种材料是否改变选片或理解结果。
不压测限制阈值，不试验播放上报。

据此再决定接口、默认档位与评论弹幕的优先级。
收益不足的分支不做，先保持成熟工具的能力边界。
本轮没有新增推荐功能、后台任务或账号写入能力。
