## A 当前判断

MoonDigest 最值得参考的是成本随阅读深度增长的路径。先筛候选，再读字幕，遇到画面问题才取帧。我们的原文保全、局部取证和修订绑定已有基础，重点应放在调用编排和证据生命周期。

建议顺序：**先测量并处理确定的重复，再验证视觉短会话和按任务选包。** 不能以减少 token 为由跳过关键画面，也不能把压缩后的笔记当成完整原文。

本轮只调研并登记方向。没有修改生产代码、启动新模型调用、安装 MoonDigest 或调整后台任务。

## B MoonDigest 值得借鉴什么

本轮对照固定于 [8bb8465](https://github.com/PathGao/MoonDigest/commit/8bb84657c67fde97dde5e894af7cbfc5f1294c03)，提交时间为北京时间 2026-11-08 01:20。只作源码分析，未实测其速度。

| 机制 | MoonDigest 实现 | 对当前 Reader 的启发 |
|---|---|---|
| 先粗后细 | 标题与简介初筛，再用字幕细看；允许拿不准 | 可以增加候选排序层；不能把标题判断登记成已经读过内容 |
| 轻量获取 | 借浏览器原生字幕，按指定秒数取画面 | 我们已有 B 站轻预览和字幕优先；继续补轻路径，不替换本地 ASR 与精确媒体能力 |
| 紧凑交付 | MCP 默认输出时间戳文本，精确结构另选 raw | 我们已有 reading/evidence；还可减少重复元数据、长 JSON 和非必要字段 |
| 输入预算 | 字幕上限 60000 字符，历史上限 40000 字符 | 借鉴显式预算和截断提示；我们的原文仍应保留并可续读 |
| 原图按需 | 默认最大宽度 1280，单帧请求 | 预览与精查分开；分辨率和裁剪需服从小字、图表等取证要求 |

两点需要区分。它的 Skill 提醒不要打印 base64 文本，但 [MCP 仍返回原生图像块](https://github.com/PathGao/MoonDigest/blob/8bb84657c67fde97dde5e894af7cbfc5f1294c03/mcp/server.js#L345)。这解决文本膨胀，**没有实现图片退出主上下文**。

它的 [长字幕策略是抽行并截断](https://github.com/PathGao/MoonDigest/blob/8bb84657c67fde97dde5e894af7cbfc5f1294c03/extension/limits.js#L276)。侧栏会提示遗漏；细看路径只取抽样结果的 text，没有传入 step。其 MCP get_video 则仍格式化全部字幕。不能把这些入口都当成无损、自动按章加载。

分拣与提示依据：[分拣说明](https://github.com/PathGao/MoonDigest/blob/8bb84657c67fde97dde5e894af7cbfc5f1294c03/docs/TRIAGE.md)、[分拣实现](https://github.com/PathGao/MoonDigest/blob/8bb84657c67fde97dde5e894af7cbfc5f1294c03/extension/triage/triage-bg.js#L662)、[侧栏输入管理](https://github.com/PathGao/MoonDigest/blob/8bb84657c67fde97dde5e894af7cbfc5f1294c03/extension/background.js#L1000)。

## C 原图现在会被携带多久

**目前不能给交互主聊天一个准确的“后续 N 次”。** 仓库能确认交付方式和独立调用的输入。现有日志没有记录主聊天每次模型请求中的图像清单。

| 路径 | 已确认的携带方式 | 后续情况 |
|---|---|---|
| 交互式 MCP | pack 将像素编码为 ImageContent，进入宿主工具结果 | Reader 没有撤回旧图的接口；宿主保留、重放或压缩的次数未测得 |
| CLI 手动读图 | Reader 返回路径；宿主打开后才获得图片 | 路径本身只是文字；打开后的驻留仍由宿主管理 |
| 通用任务消费 | 每包启动新的 codex exec，显式传入本包图像 | 后包不自动附带前包图像；多包整理的 frames 为空，只输入阅读笔记 |
| Scroll 选片 | 当前预览图进入一次独立宿主调用 | 不继承主聊天原图；一次 CLI 尝试内的模型请求及重试仍需区分 |

```flow LR
源图资产 -> MCP 图像块
MCP 图像块 -> 主聊天历史
主聊天历史 -> 宿主管理的后续上下文
源图资产 -> 独立阅读包
独立阅读包 -> 本包观察与笔记
本包观察与笔记 -> 文字整理
```

隔离来自每次新建 exec 且没有 resume。`--ephemeral` 的作用是避免持久保存会话 rollout，不能把该参数解释为自动删除模型上下文。[OpenAI Docs：非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode#run-without-persisting-a-session)

还要分开网络与上下文：后续请求即使只传会话引用，模型也可能继续使用先前图像。Prompt cache 复用前缀计算，不能据缓存命中认定证据已退出上下文。[OpenAI Docs：Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

## D 本轮确认了哪些损耗

| 证据 | 结果 | 能说明什么 |
|---|---|---|
| 超大 reading 结果的分页复现 | 2 个源帧 ID 各出现 2 次，完整分页共打包 4 个 MCP 图像块 | 先读页与后续完整证据页存在重复像素交付 |
| 现存 13 份宿主日志 | 5 份带 usage；其中含工程夹具和真实通路诊断 | 可回查总输入和缓存计数；不能统计成生产性能基准 |
| 两个历史任务的失败尝试 | 各 3 次使用相同 packet_id 和图片内容 | 重试会重新提供整包；缺少 usage 不能算作零消耗 |
| 既有最小请求诊断 | 成功请求记录 input_tokens=16954，cached_input_tokens=0 | 固定宿主输入可能很可观，值得拆账；不是每次必然相同的常数 |
| 同批带图诊断 | input_tokens=17221，cached_input_tokens=0 | 提示词和输出要求也不同，不能用两数相减计算图片 token |

分页复现只调用 pages 和 pack，没有调用模型。它证明交付重复，**不证明宿主计费次数或主聊天重放次数**。实际任务在不需要完整证据时可以提前停止分页，这也不能代替修正重复交付。

复现见 `审计脚本`（本地留证）与`结果 JSON`（本地留证）。日志原用途见[阶段 3/4 验证](../../validation/stage34-content-consumption-20261106/report-source.md)和[宿主通路诊断](../../validation/host-route-20261106/report-source.md)。

## E 提速应同时看哪些成本

| 当前实现 | 可能的损耗 | 下一步的判断依据 |
|---|---|---|
| 无既有媒体时，内容目录准备 dense 预览，最多 48 帧 | 文字导航也会准备视觉资产 | 先用文字能否完成当前任务；视觉需求出现时再补 |
| 消费前先补齐所选语音轨，再固定每 4 个时间块一包 | 默认每包约 8 分钟，常规最多选 12 帧；局部问题也遍历全文 | 按任务选相关块；完整笔记任务仍覆盖全部所需正文 |
| 每包独立启动宿主 | 固定输入、连接和推理启动可能抵消小包节省 | 在上下文上限内按文本量和视觉需求选包，比较整项任务耗时 |
| 项目参考全文每包再带入 | 每文件允许到 2 MB，无总提示词预算 | 按当前任务选参考段，保留原文件与哈希以供回查 |
| 多包最后输入全部笔记 | 输出过长和最后整理可能成为新的瓶颈 | 让中间产物保留事实、引文、疑点和定位，控制无关叙述 |
| 交付仅限制 JSON 字节与图片文件字节 | 8 MB 图片预算不能代表视觉 token 预算 | 同时记录宽高、图像数量、模型及实际可见的 usage |

压 JPEG 主要影响文件与传输；视觉 token 还取决于模型、尺寸和 detail。拼图也不能仅按“图片块更少”判断省多少，小字可读性需要一起验证。[OpenAI Docs：图像输入计量](https://developers.openai.com/api/docs/guides/images-vision#calculating-costs)

这些是静态代码确认的候选损耗，尚未完成逐项收益对照。

## F 怎样让证据离开主上下文

**最可控的办法，是让原图先进入有界的视觉短会话。** 主会话得到文字证据记录和回查标识。已有主聊天中的旧图，仍需宿主支持历史裁剪或替换，Reader 无法追溯清除。

```flow LR
任务与疑点 -> 已有内容目录
已有内容目录 -> 选择局部源图
选择局部源图 -> 视觉短会话
视觉短会话 -> 可回查证据记录
可回查证据记录 -> 主会话推理
主会话推理 --> 局部复核请求
局部复核请求 -> 选择局部源图
```

证据记录保留来源与分 P、时间、帧 ID、像素哈希和裁剪区域。再记录材料修订、实际观察者、画面原文、观察结论和不确定项。原文与推断分开，按原资产回查，不把摘要覆盖源图。

这可以复用现有共享宿主和 Reader 资产，编排放在宿主适配或通用任务域。它是待验证的视觉观察步骤，不是已经实现的 Reader 独立语义初校。当前没有新增模型或自动纠错流程。

单次短问题直接看图可能更快。图像多、后续推理长或会反复追问时，短会话才更可能划算。让主会话收到原图后再说“忘掉图片”，以及仅改成文件链接，都不能保证图片退出模型上下文。经由短会话观察时，主会话也不能声称自己亲自核验过原图。

## G 建议怎样验证下一步

先复用既有材料，比较两类任务：长视频局部问题、需要全程正文的完整笔记。保持任务要求和关键事实一致，比较直接主会话取帧、现有独立分包、按需视觉短会话。

每次真实模型请求需要记录 request/turn/attempt 的关联，及进入模型上下文的图像 ID、哈希、尺寸和裁剪。再记录总输入、缓存输入、输出、耗时与重试；字段拿不到就记未知，不填零。

核心指标是**图像在模型请求中的累计出现次数**。同时保留新增附件数和传输字节，避免把会话引用误算成不再携带图片。分别统计同图再次取证、失败重试和宿主历史重放。

测完一次图像观察后的连续追问，并覆盖实际发生压缩的边界。没有宿主请求级可观测性时，只能报告 Reader 已交付次数，不能声称测得 N。主会话隔离方案则要确认其请求中根本没有原图。

验收同时看首次可用答案时间、全任务耗时、输入/输出与重试消耗、关键事实准确性和追问补证成功。先处理已复现的分页重复，再用结果决定短会话与包大小；不预设节省比例，不默认换小模型或牺牲准确性。
